01云计算与交付模型原稿 p.1

cloud：云技术，按需提供资源。判断"是不是云"不看机器多少，而看部署形态、服务模型与那五条特征。

四种部署形态＋EX

旧整理版只写了"Cloud 按需租用"，EX 版补上了完整的部署形态划分——这条直接对应考卷 Q1(a) 的 private / public / hybrid 分类：

Public Cloud公有云
服务商提供的环境，多租户共享、由服务商运维。
Private Cloud私有云
为单个组织专用的云环境，不公开。数据敏感、合规要求高的场景留在这里。
Community Cloud社区云
多个组织共用的环境——若干机构因共同目标（合规、行业标准、共同课题）而共享一套云。
Hybrid Cloud混合云
含有多于一种云环境（如 private + public），跨越所有权边界协同提供同一项服务。
答题考卷问"Design B 属于哪种云"，判据落到所有权与运维边界：机密数据在自有 private 侧、峰值临时租 public 侧 → hybrid。若再补一句 community 的定义，说明你掌握了完整四分法。

服务模型 Service Model

按"供应商替用户管到哪一层"划分，四层自底向上：

IaaSInfrastructure · 基础设施
最基础的一层。例：创建／管理一台虚拟机——OS 以上都归用户自己管。
FaaSFunction · 函数
函数级交付。例：生命周期很短的函数功能，事件触发、免运维、按调用计费。
PaaSPlatform · 平台
例：上传资源至平台，由平台提供运行环境。
SaaSSoftware · 软件
例：在线应用（以帐号使用），用户只管用。

五大特征

On-demand self-service按需自助
自助，重点在"自"：首先你的平台自己得有资源池，其次要体现资源绑定——用户自己就能开出资源，不必与供应商人工交互。
Broad network access广泛网络访问
通过网络随处可用。
Resource pooling资源池化
资源集中至一个池里，用户无需拥有、也无需考虑具体落在哪台机器。
Rapid elasticity快速弹性
快速弹性收缩：能迅速扩张，也能迅速收回。
Measured service可计量服务
用量可计量（按核时／调用计费的基础）。
旁注上面几条连起来划了括号，旁边写：故全天候运行不算 cloud。一条服务 7×24 跑着，并不自动等于它就是云——判据是"按需自助 + 池化 + 弹性 + 可计量"这一整套。

CapEx 与 OpEx

CapExCapital expenditure · 资本性支出
一次性买下来的投入：自购服务器、建机房、供电制冷。
OpExOperational expenditure · 运营性支出
按使用量持续付出的开销：按小时／按核时租云主机。

云把 CapEx 转成了 OpEx——这是"按需提供资源"在财务侧的表述。峰值只持续几周时，自建的容量会被峰值锁死、全年折旧；租用则只为用到的时段付费。

在 cloud 里工作就一定高效吗＋EX

EX 版新增了一段完整问答，正好是考卷 Q1(d) 的标准答案：

结论：否定。三条理由——
  1. cloud 只改变部分工作方式，与效率无关：资源在谁手里、怎么付费，不等于它被用满了。
  2. cloud 的价值在于灵活性：若本地够用，还要把负载迁进 cloud 大可不必——因为云池化会有部分耗损与延迟。
  3. cloud 仅确保 capacity（容量／能拿到资源），而非 utilisation（利用率／有没有用满）。
答题"capacity ≠ utilisation"这一句可以直接写进答卷，比空泛地说"云不一定高效"值钱得多。

02并行计算的基本量原稿 p.2

Work / Task / Worker

Work工作
工作目标，全部运算操作的总量。使用的衡量方式：仅用 1 个 worker 时所用的时间 T₁。
Task任务
计算分片，把总工作切分得更小的片段；Task 之间可以存在依赖关系。
Worker执行单元
实际执行运算的算力载体，拾取 tasks 并执行。

依赖图与关键路径

dependency graph（依赖图）描述 Task 之间的先后约束，由它可以算出 minimum completion time（最小完成时间）。

原稿 p.2 的六任务图（A 分叉出 B、C，在 D 处汇合，D 之后再分叉到 E、F）
TaskStartFinish说明
A · 2 ms02起点
B · 4 ms26依赖 A
C · 3 ms25依赖 A
D · 2 ms68等 B(6) 与 C(5) 都完成，故从 6 起算
E · 3 ms811依赖 D
F · 1 ms89依赖 D
critical path: A → B → D → E = 2 + 4 + 2 + 3 = 11 ms
最小完成时间由最慢的一条链决定，即 11 ms；这就是 span（关键路径长度 T∞）。

数据并行与任务并行

分界线：是"同一段代码作用在不同数据上"，还是"不同的代码段前后接力"。

数据并行 Data Parallelism任务并行 Task Parallelism
执行的内容同样操作不同操作
执行的方式多次执行依次执行
典型形态x₀…xₙ 各自算出 y₀…yₙ（同一函数，不同数据）A → B → D → E 一条依赖链
常见载体GPU / SIMD / OpenMP forMPI 分阶段、OpenMP task

Amdahl 定律

S(P) = 1f + (1 − f)/P
f：串行部分所占的比例　｜　P：并行节点的数量
注：f 是性能瓶颈，所以 P 越大，增益越小。

当 workers 数 P → ∞ 时：

S ≤ 1f
absolute speedup limit 绝对加速比上限——无论加多少核，都超不过 1/f。

03集群架构与作业调度原稿 p.3 – p.5

进程、线程与并行接口

Process进程
正在运行的程序。
Thread线程
进程内部的执行单元；线程属于进程，一个进程里可以有很多线程。
MPI跨节点
在不同节点间搬运数据，将数据拆分为多个节点上的各个进程（rank 1 / rank 2 / rank 3 之间靠 message 通信）。
OpenMP单节点内
在单节点内利用全部 CPU，线程之间通过共享变量与内存交换数据——同一块内存大家都能读写，这也是后面竞态条件的根源。
SSI单系统映像
Single System Image：在 cluster workload 中利用多台电脑，物理上连接、再以软件把集群统一为完整系统。然而它仍然会受硬件故障、传输损耗等硬件方面的故障影响——软件层面的"像一台机器"，挡不住底层硬件出问题。

算力 ≠ 内存＋EX

EX 版在 MPI/OpenMP 之后直接写了两句判据，对应考卷 Q3(a)：

  • OpenMP 是单节点共享内存模型：只解决算力，不解决内存不足的问题。加线程只是加"读同一块内存的手"，不会让 128 GB 变成 600 GB。
  • MPI：每个 rank 各持一份数据，靠消息跨节点通信。因此跨节点的唯一自然选择就是 MPI——OpenMP 的共享内存语义跨机器不成立。
＋EXMPI 的所有节点相互不断通信，缺少任一节点都会导致集体等待——这也导致地理距离远对 MPI 的影响巨大，因为要互相等待，时延非常高。这句同时是考卷 Q4(d)（协同分配）与 Q9(f)（跨站点紧耦合）的答案。

集群层级与五类组件

自顶向下拆解：cluster（集群）→ node（一台计算机）→ socket（CPU 插槽）→ core（核心 · 基础单元）。

集群里按角色分工，共有五类组件：

Head node头节点
用户接入，提交 tasks；本身不做重计算。
Compute nodes计算节点
执行 tasks。
Interconnect互联网络
传输控制消息与程序数据。
Storage存储系统
提供统一的文件与数据访问。
I/O nodesI/O 节点
在节点之间搬运资源。

三种负载 HPC / HTC / HA

负载含义主指标
HPC 高性能倾尽集群算力解决复杂问题；一个 tightly coupled 的大任务time-to-solution（完工时间）
HTC 高通量完成大量独立 tasks（作业间不通信）throughput（单位时间完成的作业数）
HA 高可用发生硬件故障后，仍可持续监视平台availability（可用性）

作业能否放下

When does a job fit——两个条件必须同时满足：
  • 申请 CPU ≤ 节点空闲 CPU
  • 申请内存 ≤ 节点空闲内存

调度器与「否则」三后果＋EX

job scheduler（工作负载管理器，如 Slurm）做三件事：

  1. 为用户分配一段计算时间内的计算资源；
  2. 在已分配的资源上启动、监控任务；
  3. 根据申请量严格控制资源，解决多作业竞争。
＋EX 反例没有这种"严格按申请量控制"会怎样？EX 版把后果补全成三条：
① 资源调配失衡，相互拖慢（unfair）；
② 无法审计、失去监视；
③ 计算资源被个别用户占用。

核心指标

分配 CPU 总数：CPU allocated = tasks × CPUs_per_task（任务数 × 每个任务的 CPU 数）
核时：core-hours = CPU allocated × hours
效率：efficiency = core-hours actually used / core-hours allocated——分配了却没干活的核，会把这个数字拉低。
吞吐率：throughput——单位时间内能处理多少 tasks。
利用率：Utilisation = node-minutes used by jobs / (nodes × total minutes)——集群整体被用满了多少。

Waiting time 是从到达到真正开始跑的排队空耗；Turn-around time 从到达一直算到完成。

调度策略

Pareto 最优

Pareto optimality：有两个任务 X、Y，若 X 在平均等待时间、平均周转时间、资源利用率上均不逊于 Y，且至少有一点优于 Y，则称 X dominates Y。

原稿的核心例子：三个作业，两种调度顺序
JobNodesRuntime策略Wait / avg.WTurnaround / avg.TUtilisation
A430Policy 10, 30, 30 → 2030, 40, 40 → 36.7100%
B210Policy 20, 0, 10 → 3.310, 10, 40 → 20100%
C210Policy 2 是"第一任务即刻执行"的策略——利用率一样都是 100%，但平均等待与平均周转都明显更好，所以 Policy 2 dominates Policy 1。

但如果节点数有限（4 核驱动），要再比一次：A 先、BC 后 —— A 一个人吃满 4 个节点，B、C 只能等它跑完；BC 先、A 后 —— B、C 各占 2 个节点先把 4 个节点凑满，A 等它们跑完再独占。

Backfilling 回填调度

Backfilling：在不影响排队作业的前提下利用资源，两个条件——

  • 所需 nodes ≤ 空闲 nodes
  • 当前时刻 + 运行时刻 ≤ 排队时刻（不会把大作业的开工时间往后推）

Priority 优先级

Priority = Wage × Age + Wfs × FairShare + Wsize × Size
三项分别对应：等待时长、公平份额、作业规模。按权重分配，得分越高越优先。

Fairshare 公平份额

Fairshare = 2−usage/share
usage：用户已消耗的份额　｜　share：分配给该用户的份额。用得越多、超过自己的份额越多，这个值越小，优先级越低。

DRF 主导资源公平性

Dominant Resource Fairness：在多资源下，取用户占比最高的那一类资源比例来对比。比如一人用了 80% CPU、10% 内存，另一人用了 40% CPU、40% 内存——不能只看 CPU，要拿各自最"占便宜"的那一项来比，才不会让某种资源被悄悄吃空。

能耗

E = P × t
所以运行速度并非越快越好——提高功率缩短时间，总能耗未必下降。

04MPI 编程原稿 p.6 – p.8

MPI（Message Passing Interface，消息传递接口）：通过消息交换数据，遵循 SPMD（单程序、多数据）模型——每个进程跑的是同一份代码，只是各自的数据和 rank 不同。

SPMD 与 Hello World

#include <mpi.h>   /* MPI 库头文件 */
#include <stdio.h>
int main(int argc, char **argv)
{
    MPI_Init(&argc, &argv);                 /* MPI 初始化、启动环境 */
    int rank, size;
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);   /* 取当前进程的 rank */
    MPI_Comm_size(MPI_COMM_WORLD, &size);   /* 取总进程数量 */
    printf("Hello from rank %d of %d\n", rank, size);  /* 每个 MPI 进程都会打印一次 */
    MPI_Finalize();
    return 0;
}
＋EX 原文MPI_COMM_WORLD is a global communicator — it contains every process started；笔记旁注：消息仅在同一 communicator 内匹配。这也解释了为什么 `tag` 之外还需要 communicator：它界定"在哪个组里配对"。
  • 编译 / 运行：mpicc main.c -o main；mpirun -n 4 ./main（-n 后面是目标进程数，它决定 size 的大小）。
  • rank 取值：{0, size−1}，即 4 个进程就是 0～3，连续且互不相同。
  • 输出顺序：Hello from rank 2 of 4 / rank 0 / rank 3 / rank 1 —— 由于并行计算，输出顺序完全随机，谁先拿到终端说不准。

补的三个常用函数

MPI_Barrier屏障
计时前同步所有进程——保证起跑线一致。＋EX：它把进程强制对齐至同一时刻，但不改变操作顺序。
MPI_Wtime墙钟
返回墙钟（wall-clock）时间。
MPI_MAX取最慢
获取最慢进程的运行时间——并行程序的总耗时由最慢的那个决定。

阻塞、死锁与 Sendrecv＋EX

Blocking 阻塞

MPI_Send / MPI_Recv 均需等本地操作完成后才返回。危险：若收发双方都在等待对方，就触发了死锁（deadlock）。所以可用非阻塞函数：函数将立即返回，先把请求挂上，之后再用 MPI_Waitall 统一等。

非阻塞收发的参数

参数含义
&value接收／发送缓冲区，数据存入这个变量
1元素个数
MPI_INT数据类型
0信息源（source）／目标进程（destination）——第 4 位
10标签 tag，收发双方必须一致——第 5 位
MPI_COMM通信子（communicator）——第 6 位
&request取回请求句柄，供之后 Wait 使用

MPI_Sendrecv：把"发"与"收"绑进同一次调用

EX 版把这条单独写了一块，正是考卷 Q5(c) 的解法：

int other   = 1 - rank;                 /* 对话的另一方 */
int sendval = (rank == 0) ? 10 : 20;    /* 各自要发出去的值 */
int recvval = 0;                        /* 收件箱：不可与 sendval 重叠 */

MPI_Sendrecv(&sendval, 1, MPI_INT, other, 0,
             &recvval, 1, MPI_INT, other, 0,
             MPI_COMM_WORLD, MPI_STATUS_IGNORE);
＋EX 要点死锁的成因是先 MPI_Recv 再 MPI_Send，形成 circular wait；MPI_Sendrecv 把"发"与"收"绑进同一次调用，由通信子系统内部推进，于是"循环等待"无从产生。两条硬性要求：① recvval 不可与 sendval 重叠（标准禁止 sendbuf/recvbuf 重叠）；② 两侧 tag 必须一致。
＋EX 关于 BarrierMPI_Barrier 将两个 processes 强制对齐至同一时刻，但不改变操作顺序；打破死锁必须改变 communication pattern。——这一句直接就是考卷 Q5(e) 的答案：屏障不改变顺序，所以收/发次序照旧，死锁照旧。

halo 交换的完整例子

非阻塞通信最典型的用法：每个进程把自己的边界数据发给右邻居，同时从左邻居收边界。

int right = (rank + 1) % size;
int left  = (rank + size - 1) % size;
MPI_Request req[2];
MPI_Isend(halo_out, n, MPI_DOUBLE, right, 0, MPI_COMM_WORLD, &req[0]);
MPI_Irecv(halo_in,  n, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, &req[1]);
update_interior();                          /* 网格内部单元计算，与通信重叠 */
MPI_Waitall(2, req, MPI_STATUSES_IGNORE);   /* 等待，直至所有 req 完成 */
update_boundary(halo_in);                   /* 用上一个 thread 的边界更新下一个 */

作用：用相邻 thread 的边界来更新下一个 thread 的边界。关键在于 update_interior() 被夹在发收与等待之间——通信和计算重叠，这才是非阻塞的收益所在。

集合通信＋EX

Collective communication（集合通信）：一个函数调用，多个进程参与。

MPI_Bcast 广播

MPI_Bcast(&step, 1, MPI_INT, 0, MPI_COMM_WORLD);   /* 将同一个变量广播至所有进程 */

Rank 0 的 step = 100 会被复制到 Rank 1 / 2 / 3，大家的 step 都变成 100。

MPI_Scatter / MPI_Gather 分发与汇总

适用于广播多个不同的数据——Bcast 发的是同一份，Scatter 会把数组切开一人一块。

int sendbuf[4] = {10, 20, 30, 40};
int recvbuf;
int result[4];
MPI_Scatter(sendbuf, 1, MPI_INT, &recvbuf, 1, MPI_INT, 0, MPI_COMM_WORLD);
MPI_Gather(&recvbuf, 1, MPI_INT, result,   1, MPI_INT, 0, MPI_COMM_WORLD);

第 1 组（sendbuf 那侧）= 发送方的元素；第 2 组（result 那侧）= 接收方的元素；0 = 源进程（根进程）；MPI_COMM_WORLD = 通信子。Scatter 把 {10,20,30,40} 切成一人一个，Gather 再把各位的结果收回根进程。

MPI_Reduce 归约

归约运算：将多个进程的结果处理，并保存在 root（根进程）。

double local = 0.0;
for (long i = rank; i < n; i += size) { /* 每个进程分到的部分 */ }
double total = 0.0;
MPI_Reduce(&local, &total, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
参数含义
&local, &total发送／接收缓冲区
1每个进程的元素数（count）
MPI_DOUBLEtype（数据类型）
MPI_SUMreduction operation（对元素进行什么操作）
0结果保留在哪个进程（root）
MPI_COMM_WORLD通信子
＋EX 两条新注释 ① MPI_Reduce 从设计上就仅把结果保留至 root，从而减少通信开销；其它进程的 recvbuf 里都是 garbage，标准不保证里面有什么。
② MPI_Allreduce：归约后把结果写回所有进程，相当于 Reduce + Bcast。
＋EX 集合通信为什么优于手写集合通信写法简洁、统一格式、可读性高、多进程下延迟低，故通常优于手写 Send/Recv 等。

通信时间模型

T ≈ α + nβ
α：Latency 延迟——与数据量无关的固定启动开销
β：bandwidth 带宽——每字节的传输代价；n 是数据量
这条式子说明：小消息几乎全被 α 支配，所以"多发几次小包"往往比"一次发大包"更亏。

05OpenMP 编程原稿 p.9 – p.10

MPI 管的是节点之间，OpenMP 管的是节点内部。OpenMP 是 fork-join 模型的一种实现。

Fork-Join

Fork-Join Parallelism（分叉-合并）：复用 threads，降低开销。主线程在 fork 处分出若干线程并行跑，到 join 屏障处全部收回来，主线程继续往下。

#include <omp.h>
#pragma omp parallel                      /* 创建 fork-join */
{
    do_work(omp_get_thread_num());        /* 每个 fork 独立跑，时间可能不同，与 MPI 类似 */
}                                         /* join 屏障：每个 fork 全结束后才可继续 */
注意普通的 Fork-Join 仅对 threads 做合并，对数据无处理。数据怎么分、怎么汇总，是你自己的事——这正是下面一堆同步手段要解决的问题。

竞态与四种同步手段

Race condition（竞态条件）：在 fork 出来的线程进行写入时，可能会相互覆盖。EX 版旁注把机制写得更清楚：若在写回（write back）之前直接作废，那么就会被覆盖——即"读—改—写"三步被打断。

手段保护范围开销适用写法
reduction 归约整个变量最低合并变量#pragma omp parallel for reduction(+:total)
atomic 原子一条语句低单变量或嵌套#pragma omp atomic 仅保护这一行
critical 临界区一个代码块较高，易退化为串行互斥语句#pragma omp critical
Omp_lock_t 手动锁你指定的任意区间看你写得多细跨语句保护omp_init_lock / omp_destroy_lock / omp_set_lock / omp_unset_lock

reduction：每个线程各自攒一份局部结果，退出时自动合并，不需要手动加锁。critical：同一时间只允许一个 thread 进入，只适用于互斥语句，代码容易退化为串行。手动锁：未加锁／未解锁就会锁死——给你最大的自由度，也把正确性的责任全交给了你。

数据作用域与 default(none)＋EX

每个变量在线程之间到底是"共用一份"还是"各有一份"，由作用域决定。

shared共享
所有 threads 共享的变量，例：a[n][n]。
private私有
每个 thread 拥有独立副本值，例：循环部分的 i。（不初始化）
firstprivate首值私有
最开始的初始化副本值，例：代码开头 int a = 1; 的值会被带进每个副本。
lastprivate末值私有
并行结束时最后一次循环的副本变量值，会被带回外面的变量里。
reduction归约
每个 thread 独立执行，最后归约，例：total。
＋EX 新增default(none)：forces data-scoping decisions —— 任何没在 DataScope 里声明的变量都会报错，从而消除隐性隐患。这是考卷 Q7(e) 的标准答案：把"忘记声明导致意外共享"这类隐蔽竞态从运行期挪到编译期暴露。

task 与 depend

OpenMP 也能做细粒度的任务并行：用 task 把活拆开，用 depend 声明谁依赖谁。

#pragma omp parallel
#pragma omp single                    /* 仅一个主 thread 创建任务 */
{
    #pragma omp task depend(out:a)
    load_level(a);

    #pragma omp task depend(in:a) depend(out:b)     /* in：输入项  out：输出项 */
    build_navigation(a, b);

    #pragma omp task depend(in:a) depend(out:c)
    build_visibility(a, c);

    #pragma omp task depend(in:b, c)
    publish_level(b, c);
}

依赖链：① load_level → out: a；② 两个 build 都 in: a，可以并行；③ publish 要等 b、c 都完成。depend 只声明数据依赖，实际执行顺序由运行时自己排。

06并行性能度量原稿 p.11 – p.12

Measuring Parallel Performance 建立在两个自变量上：P（核心数量）与 N（问题规模）。

T / S / E / C

T(P, N)：Runtime，运行时间。
S(P, N) = T(1, N) / T(P, N)　—— Speedup 加速比，判断变快了多少倍（分子单核串行耗时、分母 P 核并行耗时）。
E(P, N) = S(P, N) / P　—— 并行效率 Efficiency，加进来的每个核到底贡献了几成。
C(P, N) = P · T(P, N)　—— Parallel cost 并行开销，代表整个程序消耗的算力总量；理想情况应等于 T(1, N)。

强缩放与弱缩放

同样是加核，问题规模不变还是跟着变大，结论完全相反。

Amdahl's Law（N 不变）Gustafson's Law（P 不变、负载随核数放大）
公式SA(P) = 1 / (S + (1 − S)/P)SG(P) = S + P(1 − S)
缩放类型strong scaling 强缩放weak scaling 弱缩放
含义固定负载下的 speedup缩放负载下的 speedup
趋势效率持续下降——P 越多，增益反而越来越少串行部分的比例被摊薄，效率可保持较高
效率式E = S/PN(P) = P · N₁；E = T(N₁) / T(P, N)

为什么两条曲线差这么多：Amdahl 假设活就那么多，核多了必然有人闲着；Gustafson 假设活可以跟着变多，核多了每人干原来那份。现实里选哪条，取决于你的问题能不能扩大规模。

四条总结＋EX

EX 版在性能度量末尾加了一段"无论 Amdahl 还是上面各类加核问题都这样看"的四步检查法——这是做题的万能骨架：

  1. 看效率：例如 1 → 20 核效率下降了 a%，1 → 25 核下降了 b%，若 b% > a% 就说明加核的边际收益在恶化。
  2. 加核会增加通信开销／延迟，所以"加 N 核就提 N 倍"纯属幻想。
  3. T = Tparallel + Tserial + Tcommunication + Timbalance——先降低串行度再来谈加核。
  4. C = P · T(1, N)：成本会爆炸，堆核的成本很高。
＋EX 用途这段可以直接回答考卷 Q8(f)"改用 64 核是否划算"：第 1 条给趋势、第 2 条给物理原因、第 3 条给分解式、第 4 条给成本结论。

Work Law 与并行度

TP ≥ max( T₁P , T∞ )
Work and span：工作量下界，用来标记执行时间的边界，取最大值。
T₁：total work，所有任务依次串行的时间　｜　T∞：critical / span path length，有 ∞ 个 P 时的执行时间（必要时间）
由此可以得出系统的 parallelism（并行度）：关键不在 processors 数，而在路径。
并行平均度　A = T₁ / T∞ —— 理论上最大同时运行的任务数，也是"无限核下的理论 speedup 上限"。
并行松弛度　σ = A / P ——　σ > 1：任务足够多；σ < 1：核心闲置。

例题与勘误

原稿 p.12 的例题：A 2ms、B 6ms、C 4ms、D 3ms、E 5ms、F 2ms，两条分支 A→B→D→F 与 A→C→E→F，P = 4 个核心。

T₁ = 2 + 6 + 4 + 3 + 5 + 2 = 22 ms
T∞ = max(2+6+3+2, 2+4+5+2) = 13 ms（两条分支等长）
A = T₁ / T∞ = 22 / 13 ≈ 1.69
T₁/P = 22/4 = 5.5 ms
TP ≥ max(5.5, 13) = 13 ms —— 被关键路径卡住，加核也没用
勘误手写原稿这一步写的是 T∞ = 2 + 6 + 5 + 2 = 15 ms，把 B（6ms）与 E（5ms）串在了同一条路径上；但按图示 B、E 分属两条不同分支，最长路径应为 A→B→D→F 或 A→C→E→F，两者都等于 13 ms。考试按 13 ms 作答，并写清"两条分支等长"。

07分布式计算与 Grid原稿 p.13 – p.14

Cluster / Grid / Cloud / Edge

Distributed Computing（分布式计算）：大量通过网络连接的独立设备，包含 Cluster、Grid、Cloud、Edge 四种形态。而 Cluster（集群）是紧耦合（tightly coupled）的节点，相当于一台放大版的系统。

关键区别：Cluster 与 Grid 的区别在于 所有权是否唯一。
四者的边界不是技术，而是"这批机器归谁"和"资源离用户多远"。

Grid 的运作方式：provider mode（独立所有者）通过 middleware（中间件），将多个不同的资源汇聚至一处，完成一项共同的任务；它们的地点、硬件、系统等均可能不同。而 user-node 看到的，只是一个单一入口的 useful pool（资源池）——底下有多杂，用户看不到。

VO 虚拟组织

VO（Virtual Organization，虚拟组织）由五样东西构成：

temporary临时的
任务期间成立，任务结束即解散。
shared goal共同目标
大家一起要完成的那件事。
membership成员资格
谁在里面、谁不在。
access rights访问权
能访问什么、能用哪些资源。
rules规则
认证授权审计、使用策略、结算方式。

它们共享使用权，但并不会合并——"一起干一件事"不等于"变成一家"。

本地优先＋EX

本地优先：当本地有任务时，Grid 将排队任务自动分配到其它资源上。

＋EX 新增一句同时对中断的任务要补偿或重新运行。——这正是考卷 Q9(c)「京都突然撤回一半机器，中间件应如何响应」的完整答案：既要把排队任务改派到别处，也要对被强制中断的任务给出补偿／重跑语义。

Grid 四层与两条边界

层名称职责
Layer 1Application 应用层解决用户实际问题（user workflow application）
Layer 2Middleware 中间件层协调 user 与 provider 的供求（resource broker）
Layer 3Resources 资源层暴露可用 capability（compute cluster）
Layer 4Fabric 织构层保障 capability 能被访问（physical CPUs & network hardware）
两条边界Middleware 与 VO 不会凭空创造资源——它们只是把已有的东西组织起来；同时，同一个机构可能既为 user 也为 provider。

两次辨析

例一：500 台电脑算什么

500 台电脑，under one administrative domain，那就是 cluster。若想变为 Grid，则需要通过 grid middleware 对外暴露，并建立相同的 access policies（访问策略）。判据还是那一条：所有权与管理边界是否唯一。

ClassAd

Grid 里描述"谁要什么、谁给什么"的方式：Job——我需要什么？　Machine——我能给什么 + 策略。

密钥对＋EX

Key pair（密钥对）：一对数学上配对、用途上互补的密钥。

动作用哪把钥匙方向
Encrypts data for owners　加密数据公钥（后缀 .pub，shared openly 公开分享）发给所有者 →
Decrypts received data　解密数据私钥（无后缀，remain secret 必须保密）← 收到后解开
Verifies digital signatures　验证签名公钥← 校验对方身份
Create digital signatures　创建签名私钥自己签 →

两条容易搞错的：

  • ① 公钥不需保密，但公钥与身份需要绑定，故保护公钥也很重要——公钥被看到没关系，被换掉才是灾难。
  • ② 私钥通常是硬件载体，禁止发送给他人，否则就失去了意义。
＋EX 新增后果链一旦私钥泄露，任何人都可以以被泄露者的身份享受服务，且无法撤销。——这是考卷 Q10(b)「为什么绝不能把长期私钥拷到远端」最有力的一句：不可撤销 + 身份被冒用。

PKI 与 X.509

PKI = 一个 connecting public keys to trusted identities 的体系，帮助使用者确认某把公钥确实属于它所声称的网站、组织等。它做的两件事：核验身份 + 签发证书，从而确定身份与公钥的绑定可信。

X.509 certification：证书是一份公开的、被 CA 数字签名的声明，绑定 identity（身份）与 Public key（公钥），并说明 validity 有效期与 constraints 约束。CA 验证身份后签发证书，于是"身份—公钥"的绑定可以被信赖。

Proxy 与 SSH 证书＋EX

Proxy 证书

特点是 short lifetime（短寿命），并可进一步施加约束。Proxy 有自己的私钥签名；登录 server 时，用 Proxy certification 里的公钥验证，故不需要用户私钥——这就是它存在的理由：把长期私钥留在本地，只放出一把短命的替身。

＋EX 关键补充因此，过期 proxy 被泄露也不能认证。——直接回答考卷 Q10(g)：过期即失效，验证方会拒绝。
＋EX 答题提示（原文）回答 Proxy 优点时，一定要说明保护 private key 的重要性，并说明分发 private key 的缺点——因为 proxy 与私钥无关，私钥永不泄露，即使 proxy 泄露影响也有限。优点和代价要成对讲，只讲一半不算答完。

SSH 证书

让用户使用 CA 签名的公钥，并证明自己拥有私钥，以登录 SSH server。证书里写明 principal（身份）和 lifetime（有效期）。服务器上三个文件各管一件事，-I 与 -Z 让每次被使用都能追溯签发记录：

文件是什么怎么用
id_grid私钥绝不离身
id_grid.pub公钥用来交由 CA 签名
id_grid-cert.pubSSH 证书（已签名的）登录时给 server 验证
Trusted CA + valid certification + allowed principal + private-key proof ⇒ login accept
四件事同时成立，登录才成功。少任何一项都不行。

零信任

Zero-trust decisions（零信任决策）：用户不会因为处于组织内部就被信任，仍然需要走验证流程。

一句话"在内网"不是身份，"走完验证"才是。

09GPU 与异构计算原稿 p.17 – p.18

CPU 与 GPU 的分工＋EX

两者的设计目标根本不是同一件事：一个要把延迟压到最小，一个要把吞吐拉到最大。

CPU最小化 latency
Powerful core：大缓存（Large caches）+ 复杂控制逻辑（Complex control），让少数几条线程尽快跑完。
GPU最大化 throughput
Many threads hide latency：用大量线程把延迟藏起来，擅长处理大量可反复利用的独立元素。
＋EX 新增判断CPU 可以尽快跑完"串行分支多、启动开销比运行开销大"的任务。反过来——短的并行链、heavily branching（分支多）、过多的并行操作这三类都不适合 GPU：启动与调度开销会吃掉并行收益。

kernel 与数据搬运

host（CPU）与 device（GPU）之间隔着一次显式数据搬运：host memory ⇄ device memory。数据一旦上了显存，就在设备侧反复运算；只有过这条搬运线，才产生换边的代价。

＋EX 开销分解每次搬运 = 搬运延迟 + 串行搬运 + 小计算的启动开销大。故通常在 GPU 中经过多次运算后，仅把最终结果传回 CPU。也因此，把操作从 GPU 转到 CPU 会因为搬运数据效率奇差。

kernel 是什么

kernel（核函数）：GPU 对许多元素执行的同一个函数，用大量独立线程提供并行工作，让 GPU 始终保持忙碌；由 index 挑选元素，元素间无通信。

写法是否适合原因
a[i] = update(a[i])适合每个元素独立取、独立算、独立写，元素之间没有关系
b[i] = b[i-1] + c[i]不适合元素之间存在 latency —— 下一个元素要用上一个的结果，只能串着走

框架抽象层

能不设计 kernel 就不设计——越往下设计越复杂，且回报率低。中间一层是 Framework（框架，如 PyTorch、TensorFlow 等模型），可以用它代替程序员做三件事：

  • device-memory management　设备内存管理
  • host-device movement　主机—设备数据搬运
  • selection and launch of GPU kernel　选择、调用核函数

p.8MPI_Reduce 只把结果留在 root；其它进程 recvbuf 是 garbage，标准不保证Q6(c) 只有 rank 0 能用
p.8MPI_Allreduce = Reduce + BcastQ6(d)
p.8集合通信写法简洁、统一格式、可读性高、多进程延迟低，优于手写 Send/RecvQ6(e)
p.10default(none)：forces data-scoping decisions，未声明即报错，消除隐性隐患Q7(e)
p.11四条总结：看效率趋势 / 加核增通信开销（加 N 核提 N 倍是幻想）/ 用四项时间分解降低串行度 / C = P·T 成本爆炸Q8(f) 64 核是否划算；Q8(g) 效率下降
p.13本地优先之外：对中断任务要补偿或重新运行Q9(c) 京都撤回机器
p.15私钥泄露 → 任何人可以以被泄露者身份享受服务，且无法撤销Q10(b) 绝不外传私钥
p.16过期 proxy 被泄露也不能认证；Proxy 答题提示（优点与代价成对讲）Q10(f)(g)
p.17CPU 适合"串行分支多、启动开销 > 运行开销"的任务；每次搬运 = 延迟 + 串行搬运 + 小计算启动开销Q11(a)(b)
结论旧整理版里"笔记未收录"的三处（MPI_Sendrecv、Barrier 与死锁、default(none)）以及另带 On-demand/Allreduce/集合通信优点/过期 proxy 等 9 处"部分收录"，在 EX 版里全部补齐。据此重写的考卷答案，66 小问中已有 65 处可直接引用笔记原文，仅剩 Q2(f)「为何 16 核给不了 16×」需要自己用笔记里的 A、σ、Work Law 推一步。
