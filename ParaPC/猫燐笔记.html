01云计算与交付模型原稿 p.1

cloud：云技术，按需提供资源。

服务模型 Service Model

按"供应商替用户管到哪一层"来划分，四层从底层往上依次是：

IaaSInfrastructure · 基础设施
最基础的一层。例：创建／管理一台虚拟机。

PaaSPlatform · 平台

SaaSSoftware · 软件
例：在线应用（以帐号使用）。

五大特征

On-demand self-service
按需自助。
Broad network access
广泛网络访问。
Resource pooling
资源池化。
Rapid elasticity
快速弹性收缩。

可计量服务。
原文旁注 上面几条特征连起来划了个括号，旁边写：故全天候运行不等于 cloud。 一条服务 7×24 跑着，并不自动等于它就是云——云的判据是"按需自助 + 池化 + 弹性 + 可计量"这一整套特征。

CapEx 与 OpEx

Capital expenditureCapEx · 资本性支出
一次性买下来的投入，比如自己买服务器、建机房。

02并行计算的基本量原稿 p.2

Work / Task / Worker

Work工作
工作目标，全部运算操作的总量。
使用的衡量方式：仅用 1 个 worker 时所用的时间。
Task任务
计算分片，把总工作切分得更小的片段。
Task 之间可以存在依赖关系。
Worker执行单元
实际执行运算的算力载体，抽取 tasks 并执行。

数据并行与任务并行

两种并行方式的分界线：是"同一段代码作用在不同数据上"，还是"不同的代码段前后接力"。

Amdahl 定律

Amdahl's Law：P 个 workers 下的最大加速比。

S(P) = 1 f + (1 − f) / P
f：串行部分所占的比例　｜　P：并行节点的数量

注：f 是性能瓶颈，所以 P 越大，增益越小。

当 workers 数 P → ∞ 时：

S ≤ 1f
absolute speedup limit　绝对加速比上限 —— 无论加多少核，都超不过 1/f。

03集群架构与作业调度原稿 p.3 – p.5

进程、线程与并行接口

Process进程
正在运行的程序。
Thread线程
进程内部的执行单元。线程属于进程。

MPI：跨节点

MPI：在不同节点间搬运数据，将数据拆分为多个节点上的各个进程。

OpenMP：单节点内

OpenMP：在单节点内利用全部 CPU，线程之间通过 共享变量与内存 交换数据。

SSI 单系统映像

SSI（Single System Image，单系统映像）：在 cluster workload 中利用多台电脑， 物理上连接，再以软件将集群统一为完整系统。

然而 它仍然会受硬件故障、传输损耗等硬件方面的故障影响 —— 软件层面的"像一台机器"，挡不住底层硬件出问题。

集群的层级结构

自顶向下拆解：

集群里按角色分工，共有五类组件：

Head node头节点
用户接入，提交 tasks。
Compute nodes计算节点
执行 tasks。
Interconnect互联网络
传输控制消息与程序数据。
Storage存储系统
提供统一的文件与数据访问。
I/O nodesI/O 节点
在节点之间搬运资源。

执行时间模型与三种负载

Ttotal ≈ TparallelworkP + Tserial + Tcommunication + Timbalance
总时间 = 并行部分摊到 P 个 worker 上的时间 ＋ 串行部分 ＋ 通信开销 ＋ 负载不均造成的空等。 后面三项都是加不掉的"税"。

按用途，集群承担三种不同的负载：

HPC高性能
倾尽集群算力解决复杂问题。
HTC高通量
完成大量独立 tasks。
HA高可用
发生硬件故障后，仍可持续监视平台。

作业能否放下

When does a job fit：一个作业能被放到某个节点上，必须同时满足两个条件 ——

申请 CPU ≤ 节点空闲 CPU
申请内存 ≤ 节点空闲内存

调度器与核心指标

job scheduler（工作负载管理器，如 slurm）做三件事：

  • 为用户分配一段计算时间内的计算资源；
  • 在已分配的资源上启动、监控任务；
  • 根据申请量严格控制资源，解决多作业竞争。
反例 没有这种"严格按申请量控制"的话，会出两类问题：资源调配失衡、计算资源被个别用户占用。

分配量与成本

CPU allocated = tasks × CPUs_per_task
分配 CPU 总数 = 任务数 × 每个任务的 CPU 数
core-hours = CPU allocated × hours
核时 = 分配的 CPU 总数 × 运行小时数

效率与吞吐

efficiency = core-hours actually used core-hours allocated
实际所用 CPUs ÷ 分配 CPU 总数 —— 分配了却没干活的核，会把这个数字拉低。

throughput（吞吐率）：单位时间内能处理多少 tasks。

等待与周转

Utilisation = node-minutes used by jobs nodes × total minutes
所有运行节点时长 ÷ 节点总时长 —— 集群整体被用满了多少。

调度策略

Pareto 最优

Pareto optimality（帕累托最优）：有两个任务 X、Y， 如果 X 在平均等待时间、平均周转时间、资源利用率上均不逊于 Y，且至少有一点优于 Y， 则称 X dominates Y。

下面这个例子是笔记里的核心：三个作业，两种调度顺序，指标完全不同。

三个作业的规模
JobNodesRuntime
A430
B210
C210
两种调度策略的指标对比
策略 Waitavg. W Turnaroundavg. T Utilisation
Policy 1 0, 30, 3020 30, 40, 4036.7 100%

Policy 2 是第一任务即刻执行的策略 —— 利用率一样都是 100%，但平均等待和平均周转都明显更好， 所以 Policy 2 dominates Policy 1。

但如果节点数有限呢？若为 4 核驱动，则哪个更好：

  1. A 先，BC 后：A 一个人吃满 4 个节点，B、C 只能等它跑完再并行；
  2. BC 先，A 后：B、C 各占 2 个节点，先把 4 个节点凑满，A 等它们跑完再独占。

Backfilling 回填调度

Backfilling（回填调度）：在不影响排队作业的前提下利用资源。要同时满足两个条件 ——

所需 nodes ≤ 空闲 nodes
当前时刻 + 运行时刻 ≤ 排队时刻

小作业可以从队列后面"插空"塞进大作业等待的时间缝隙里，前提是不会把大作业的开工时间往后推。

Priority 优先级

Priority = Wage × Age + Wfs × FairShare + Wsize × Size
三项分别对应：等待时长、公平份额、作业规模。 根据权重分配，得分越高越优先。

Fairshare 公平份额

Fairshare = 2(−usage/share)
usage：用户已消耗的份额　｜　share：分配给该用户的份额
用得越多、超过自己的份额越多，这个值越小，优先级就越低。

DRF 主导资源公平性

Dominant Resource Fairness（主导资源公平性）： 在多资源下，取用户占比最高的那一类资源比例来进行对比。

比如一个人用了 80% 的 CPU、10% 的内存，另一个用了 40% 的 CPU、40% 的内存 —— 不能只看 CPU，要拿各自最"占便宜"的那一项来比，才不会让某种资源被悄悄吃空。

能耗

E = P × t
所以 运行速度并非越快越好 —— 提高功率缩短时间，总能耗未必下降。

04MPI 编程原稿 p.6 – p.8

MPI（Message Passing Interface，消息传递接口）：通过消息交换数据， 遵循 SPMD（单程序、多数据） 模型 —— 每个进程跑的是同一份代码，只是各自的数据和 rank 不同。

SPMD 与 Hello World

#include <mpi.h>    /* MPI 头文件 */
#include <stdio.h>

int main(int argc, char **argv)
{
    MPI_Init(&argc, &argv);        /* MPI 初始化、启动环境 */

    int rank, size;
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);   /* 取当前进程的 rank */
    MPI_Comm_size(MPI_COMM_WORLD, &size);   /* 取总进程数量 */

    printf("Hello from rank %d of %d\n", rank, size);   /* 每个 MPI 进程都会打印一次 */

    MPI_Finalize();
    return 0;
}

MPI_COMM_WORLD 是全局通信子，代表这次启动的全部 MPI 进程。

勘误 原笔记把取进程数那一行也写成了 MPI_Comm_rank，实际取总进程数用的是 MPI_Comm_size —— 两者参数形式一样，但一个取 rank、一个取 size。

编译与运行

# 编译
mpicc main.c -o main

# 运行：-n 后面是目标进程数，比如 4
mpirun -n 4 ./main

输出

Hello from rank 2 of 4
Hello from rank 0 of 4
Hello from rank 3 of 4
Hello from rank 1 of 4

由于并行计算，输出顺序完全随机 —— 进程 ID 是 0～3 这 4 个，但谁先拿到终端说不准。

补充的三个常用函数

MPI_Barrier
计时前同步所有进程 —— 保证起跑线一致。
MPI_Wtime
返回墙钟（wall-clock）时间。
MPI_MAX
获取最慢进程的运行时间 —— 并行程序的总耗时由最慢的那个决定。

阻塞、死锁与非阻塞

Blocking 阻塞

MPI_Send / MPI_Recv 均需等本地操作完成后才返回。

危险 若收发双方都在等待对方，就触发了死锁（deadlock）。

所以可用非阻塞函数：函数将立即返回，先把请求挂上，之后再用 MPI_Waitall 统一等。

MPI_Isend / MPI_Irecv(&value, 1, MPI_INT, 0, 10, MPI_COMM, &request);
非阻塞收发函数的参数
参数含义
&value接收／发送缓冲区，数据存入这个变量
1元素个数
MPI_INT数据类型
0信息源／目标进程
10标签 tag，收发双方必须一致
MPI_COMM通信子
&request取回请求句柄，供之后 Wait 使用

halo 交换的完整例子

这是非阻塞通信最典型的用法：每个进程把自己的边界数据发给右邻居，同时从左邻居收边界。

int right = (rank + 1) % size;
int left  = (rank + size - 1) % size;
MPI_Request req[2];

MPI_Isend(halo_out, n, MPI_DOUBLE, right, 0, MPI_COMM_WORLD, &req[0]);
MPI_Irecv(halo_in,  n, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, &req[1]);

update_interior();   /* 网格内部单元计算，与通信重叠 */

MPI_Waitall(2, req, MPI_STATUSES_IGNORE);   /* 等待，直至所有 req 完成 */

update_boundary(halo_in);   /* 取上一个 thread 的边界，更新下一个 thread 的边界 */
作用 用相邻 thread 的边界来更新下一个 thread 的边界。关键在于 update_interior() 被夹在发收与等待之间 —— 通信和计算重叠，这才是非阻塞的收益所在。

集合通信

Collective communication（集合通信）：一个函数调用，多个进程参与。

MPI_Bcast 广播

MPI_Bcast(&step, 1, MPI_INT, 0, MPI_COMM_WORLD);

将同一个变量广播至所有进程。

MPI_Scatter / MPI_Gather 分发与汇总

适用于广播多个不同的数据 —— Bcast 发的是同一份，Scatter 会把数组切开一人一块。

int sendbuf[4] = {10, 20, 30, 40};
int recvbuf;
int result[4];

MPI_Scatter(sendbuf, 1, MPI_INT, &recvbuf, 1, MPI_INT, 0, MPI_COMM_WORLD);
MPI_Gather(&recvbuf, 1, MPI_INT, result, 1, MPI_INT, 0, MPI_COMM_WORLD);
参数位置含义
第 1 组（sendbuf 那侧）发送方的元素
第 2 组（result 那侧）接收方的元素
0源进程（根进程）
MPI_COMM_WORLD通信子

MPI_Reduce 归约

归约运算：将多个进程的结果处理，并保存在 root（根进程）。

double local = 0.0;
for (long i = rank; i < n; i += size) {   /* 每个进程分到的部分 */
    /* 运算 */
}

double total = 0.0;
MPI_Reduce(&local, &total, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
参数含义
&local, &total发送／接收缓冲区
1每个进程的元素数
MPI_SUM对元素进行什么操作（求和）
0结果保存在哪个进程

通信时间模型

T ≈ α + nβ
α：Latency 延迟 —— 与数据量无关的固定启动开销
β：bandwidth 带宽 —— 每字节的传输代价；n 是数据量

这条式子说明：小消息几乎全被 α 支配，所以"多发几次小包"往往比"一次发大包"更亏。

05OpenMP 编程原稿 p.9 – p.10

MPI 管的是节点之间，OpenMP 管的是节点内部。OpenMP 是 fork-join 模型的一种实现。

Fork-Join

Fork-Join Parallelism（分叉-合并）：复用 threads，降低开销。

最简单的写法

#include <omp.h>

#pragma omp parallel          /* 创建 fork-join */
{
    do_work(omp_get_thread_num());   /* 每个 fork 独立跑，时间可能不同，与 MPI 类似 */
}                                /* join 屏障：每个 fork 全结束后才可继续 */
注意 普通的 Fork-Join 仅对 threads 做合并，对数据无处理。数据怎么分、怎么汇总，是你自己的事 —— 这正是接下来一堆同步手段要解决的问题。

竞态与四种同步手段

Race condition（竞态条件）：在 fork 出来的线程进行写入时，可能会相互覆盖。

① Reduction 归约

开销最低，适用于合并变量。

int total = 0;

#pragma omp parallel for reduction(+:total)
{
    total += values[i];
}

每个线程各自攒一份局部结果，退出时自动合并，不需要你手动加锁。

② atomic 原子

只保护一条语句，适用于单变量或嵌套场景。

int total = 0;

#pragma omp parallel for shared(total, arr, n)
for (int i = 0; i < n; i++)
{
    #pragma omp atomic
    total += arr[i];   /* 仅保护这一行 */
}

③ critical 临界区

同一时间只允许一个 thread 进入，只适用于互斥语句。

代价 临界区代码容易退化为串行 —— 保护的范围越大，并行度就损失得越多。

④ Omp_lock_t 手动锁

需要自己在代码中增加加锁／解锁，用于需要跨越多个语句保护同一份资源的情况。

omp_init_lock / omp_destroy_lock      /* 创建 / 销毁 */
omp_set_lock  / omp_unset_lock        /* 加锁 / 解锁 */

未加锁／未解锁就会锁死。手动锁给你最大的自由度，也把正确性的责任全交给了你。

手段保护范围开销适用
reduction整个变量最低合并变量
atomic一条语句低单变量或嵌套
critical一个代码块较高，易退化为串行互斥语句
Omp_lock_t你指定的任意区间看你写得多细跨语句保护，需手动配对加解锁

数据作用域 Data Scope

每个变量在线程之间到底是"共用一份"还是"各有一份"，由作用域决定。

shared
所有 threads 共享的变量，例：a[n][n]。
private
每个 thread 拥有独立副本值，例：循环里那个 i。
firstprivate
最开始的初始化副本值，例：代码开头 int a = 1; 的值会被带进每个副本。
lastprivate
并行结束时最后一次循环的副本变量值，会被带回到外面的变量里。
reduction
每个 thread 独立执行，最后归约，例：total。

task 与 depend

OpenMP 也能做细粒度的任务并行：用 task 把活拆开，用 depend 声明谁依赖谁。

#pragma omp parallel
#pragma omp single               /* 仅一个主 thread 创建任务 */
{
    #pragma omp task depend(out:a)
    load_level(a);

    #pragma omp task depend(in:a) depend(out:b)     /* in：输入项　out：输出项 */
    build_navigation(a, b);

    #pragma omp task depend(in:a) depend(out:c)
    build_visibility(a, c);

    #pragma omp task depend(in:b, c)
    publish_level(b, c);
}

06并行性能度量原稿 p.11 – p.12

T / S / E / C 四个量

Measuring Parallel Performance（并行性能度量）建立在两个自变量上：

P
核心数量。
N
问题规模。
T(P, N)：Runtime，运行时间
S(P, N) = T(1, N) T(P, N)
分子是单核串行耗时，分母是 P 核并行耗时。
Speedup 加速比 —— 判断变快了多少倍。
E(P, N) = S(P, N) P
并行效率 Efficiency —— 加进来的每个核，到底贡献了几成。
C(P, N) = P · T(P, N)
Parallel cost 并行开销 —— 代表整个程序消耗的算力总量。理想情况下应该等于 T(1,N)。

强缩放与弱缩放

同样是加核，问题规模不变还是跟着变大，结论完全相反。

Amdahl's Law —— 固定负载（N 不变）

SA(P) = 1 S + (1 − S) / P
S：串行占比（另一个加数是并行占比）
计算的是固定负载下的 speedup。

这叫 strong scaling（强缩放）：效率持续下降，代表 P 越多，增益反而越来越少。

Gustafson's Law —— 缩放负载

SG(P) = S + P(1 − S)
计算的是缩放负载下的 speedup。

这叫 weak scaling（弱缩放）：核变多的同时问题也变大，串行部分的比例被摊薄。

N(P) = P · N1   ｜   E = T(N1) T(P, N)
核数翻 P 倍，就把问题规模也放大 P 倍，再看时间涨了多少。
为什么两条曲线差这么多 Amdahl 假设活就那么多，核多了必然有人闲着；Gustafson 假设活可以跟着变多， 核多了每人干原来那份。现实里选哪条，取决于你的问题能不能扩大规模。

Work Law

Work and span：工作量下界，用来标记执行时间的边界。

TP ≥ max ( T1P , T∞ )
取最大值 —— 实际耗时不可能小于这两条下界中更大的那一个。
T1：total work，所有任务依次串行的时间
T∞：critical / span path length，当有 ∞ 个 P（核心）时的执行时间，即必要时间

并行平均度 Parallelism

A = T1T∞
理论上最大同时运行的任务数。

并行松弛度 Parallel Slackness

σ = AP
σ > 1：任务足够；
σ < 1：核心闲置。

例题

解：
T1 = 2 + 6 + 4 + 3 + 5 + 2 ms = 22 ms
T∞ = max(2+6+3+2, 2+4+5+2) = 13 ms
A = T1 / T∞ = 22 / 13
T1 / P = 22 / 4 = 5.5 ms
TP ≥ max(5.5, 13) = 13 ms
两条分支的长度都是 13ms，所以 span（关键路径）就是 13ms；work 下界只要求 5.5ms， 两者取大，最终下界是 13ms —— 说明这道题被关键路径卡住，加核也没用。
勘误 原笔记这一步记作 T∞ = 2+6+5+2 = 15ms，把 B（6ms）和 E（5ms）串在了同一条路径上； 但按图示 B、E 分属两条不同分支，最长路径应是 A→B→D→F 或 A→C→E→F，两者都等于 13ms。

07分布式计算与 Grid原稿 p.13 – p.14

Cluster / Grid / Cloud / Edge

Distributed Computing（分布式计算）：大量通过网络连接的独立设备。

而 Cluster（集群）是紧耦合的节点（tightly coupled），相当于一台放大版的系统。

关键区别 Cluster 与 Grid 的区别在于：所有权是否唯一。

Grid 的运作方式

provider mode（独立所有者）通过 middleware（中间件）， 将多个不同的资源汇聚至一处，完成一项共同的任务。它们的地点、硬件、系统等均可能不同。

而 user-node 看到的，只是一个单一入口的 useful pool（资源池） —— 底下有多杂，用户看不到。

VO 虚拟组织

VO（Virtual Organization，虚拟组织）由五样东西构成：

temporary
临时的。
shared goal
共同目标。
membership
成员资格。
access rights
访问权。
rules
规则。

它们共享使用权，但并不会合并。——"一起干一件事"不等于"变成一家"。

本地优先

当本地有任务时，Grid 将排队任务自动分配到其它资源上。

Grid 的分层

两条边界 Middleware 与 VO 不会凭空创造资源 —— 它们只是把已有的东西组织起来；
同时，同一个机构可能既为 user 也为 provider。

Grid 访问本身就有风险。一次 request access（访问请求）必须回答四个问题。

Authentication认证
对方是谁？

原文批注

A valid identity doesn't imply permission, and permission doesn't remove the need for audit.

翻译过来：有身份（认证通过）不等于能授权，授权后不等于不被监视。 —— 这四问是四件事，不能拿前一问的答案去顶后一问。

密钥对

Key pair（密钥对）：一对数学上配对、用途上互补的密钥。

动作用哪把钥匙方向
加密数据 Encrypts data for owners公钥发给所有者 →
解密数据 Decrypts received data私钥← 收到后解开
验证签名 Verifies digital signatures公钥← 校验对方身份
创建签名 Create digital signatures私钥自己签 →
两条容易搞错的

① 公钥不需保密，但公钥与身份需要绑定，故保护公钥也很重要 —— 公钥本身被看到没关系，被换掉才是灾难。

② 私钥通常是硬件载体，禁止发送给他人，否则就失去了意义 —— 私钥一旦离身，整套身份就归别人了。

PKI 与 X.509

PKI：一个 connecting public keys to trusted identities 的体系 —— 帮助使用者确认，某把公钥确实属于它所声称的那个网站、组织。

X.509 certification

证书是一份公开的、被 CA 数字签名的声明，绑定身份与公钥，并说明 validity（有效期） 与 constraints（约束）。

Proxy 与 SSH 证书

Proxy 证书

特点是 short lifetime（短寿命），并可进一步施加约束。

Proxy 有自己的私钥签名。登录 server 时，用 Proxy certification 里的公钥验证， 故不需要用户私钥 —— 这就是它存在的理由：把长期私钥留在本地，只放出一把短命的替身。

答题提示（原文） 回答 Proxy 优点时，一定要说明保护 private key 的重要性，并说明分发 private key 的缺点 —— 优点和代价要成对讲，只讲一半不算答完。

SSH 证书

让用户使用 CA 签名的公钥，并证明自己拥有私钥，以登录 SSH server。 证书里写明 principal（身份）和 lifetime（有效期）。

服务器上三个文件各管一件事，-I 与 -Z，让每次被使用都能追溯签发记录：

文件是什么怎么用
id_grid 私钥 绝不外身
id_grid.pub 公钥 用来交由 CA 签名
id_grid-cert.pub SSH 证书（已签名的） 登录时给 server 验证

零信任

Zero-trust decisions（零信任决策）：用户不会因为处于组织内部就被信任， 仍然需要走验证流程。

一句话 "在内网"不是身份，"走完验证"才是。

09GPU 与异构计算原稿 p.17 – p.18

CPU 与 GPU 的分工

两者的设计目标根本不是同一件事：一个要把延迟压到最小，一个要把吞吐拉到最大。

CPU最小化延迟
Powerful core：大缓存（Large caches）+ 复杂控制逻辑（Complex control）， 让少数几条线程尽快跑完。
GPU最大化吞吐 throughput
many threads hide latency：用大量线程把延迟藏起来， 擅长处理大量可反复利用的独立元素。
不适合 GPU 的三类 短的并行链、heavily branching（分支多）、过多的并行操作 —— 这三种情况启动与调度开销会吃掉并行收益，均不适合 GPU。

kernel 与数据搬运

数据搬运的开销大，故通常在 GPU 中经过多次运算后，仅把最终结果传回 CPU。 也因此，把操作从 GPU 转到 CPU 会因为搬运数据效率奇差。

kernel 是什么

kernel（核函数）：GPU 对许多元素执行的同一个函数， 用大量独立线程提供并行工作，让 GPU 始终保持忙碌。由 index 挑选元素，元素间无通信。

写法是否适合原因
a[i] = update(a[i])适合每个元素独立取、独立算、独立写，元素之间没有关系
b[i] = b[i-1] + c[i]不适合元素之间存在 latency —— 下一个元素要用上一个的结果，只能串着走

框架抽象层

能不设计 kernel 就不设计 —— 越往下设计越复杂，且回报率低。

Framework（框架，如 PyTorch、TensorFlow 等）可以代替程序员做的三件事：

device-memory management
设备内存管理。
host-device data movement
主机—设备数据搬运。
selection and launch of GPU kernel
选择、调用核函数。
